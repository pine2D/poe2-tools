# 背包多页恢复核对

2026-09-26，运行时0.1.93／eac9566。本轮不修改扩展代码、不升版本。

## 已完成的链路

在已入库双物品样本基础上制作测试备份：保留原站自动创建的空PoE1页，第一PoE2页改名Runed Focus，另增一个PoE2页Clipboard action，将黄玉戒指移到新增页的(0,0)，破碎手套留在第一页。UUID只标识自造存档。这是明确编辑的测试输入，不冒充原站新建动作的输出。

普通启动参数的独立无扩展Chrome先恢复未修改的双物品备份，导出与输入相等；再恢复该多页输入，导出与输入相等。最终0.1.93解包扩展的另一个普通会话恢复相同多页输入，其原生导出与无扩展结果逐字节一致。入库two-page-inventory.json来自此次原生导出，仅增加缩进。

两边逐页真实点击，并等待目标装备节点出现：Runed Focus页只显示破碎手套，Clipboard action页只显示黄玉戒指，物品UUID与导出映射一致。随后在制作页导入同一自造手套、点击Save／保存，原生目标按钮均保持两个自定义页名；中文公共动作显示“新建仓库页”。本轮只查看保存目标后关闭，没有增加第三件物品。

## 原生新建入口尚未通过

早先新建页加号、右键及quota帮助无预期界面，本轮进一步排除原生prompt／confirm被自动处理的猜测。在--no-auto-dialog会话中，英文原站加号点击后没有待处理的浏览器对话框，公开点击事件命中子DIV；没有捕获到公开error／unhandledrejection。保存→New tab也仍停留在保存目标列表。未读取原站执行源码或内部对象，尚不能解释原因，不声称功能不存在或确定是上游缺陷。

该特殊测试会话出现另一异常：恢复编辑备份后，装备详情仍在导出items内，但inventory.items摆放映射为空。等待重载后仍然如此，恢复未修改的既有样本也失败。因此不能把它归因于多页格式；换普通干净会话后，未修改与多页样本均完整恢复。两会话还存在操作历史差异，不能仅凭对照把根因锁定为--no-auto-dialog参数。

首次切换CLI启动参数曾使测试标签回到about:blank；通过标签状态和终止的等待确认后重新导航。后续特殊会话始终传入同一参数，普通验收会话独立命名，未把加载异常当扩展故障。

## 验收边界

已证实：两个PoE2页的备份恢复、原生导出、已有页切换、物品归属、自定义名称与保存目标保护。未证实：通过UI创建或重命名页、跨页拖拽／移动、跨游戏恢复及上述特殊会话异常根因。现有默认页双物品成功证据仍有效；新增对照不是所有浏览器配置的兼容保证。

本轮只改验收文档和自造样本，检查JSON内容与原生导出、git diff --check；未重跑代码测试、全仓verify或打包。交付包仍为0.1.93。
