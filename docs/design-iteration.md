# 网站与扩展的整体体验：迭代方法及推荐路线

状态：2026-11-15，构筑 A 单页交付已由用户选定并进入本地生产代码实现，尚未发布；其余界面继续按各自任务核对。本文保留探索依据与各轮历史，最新批准和实施范围见文末。

## 目标与文档边界

整体目标覆盖 **网站与扩展的全部界面：共享设计语言，同时根据各自功能安排信息和操作**。构筑导入、展示局促和网站割裂是用户举出的例子，不是优化范围的边界。既要检查单个界面，也要检查网站、弹窗、侧栏与第三方页面之间的体验是否连续。

用户于 2026-10-24 对构筑使用明确：“先汉化并下载，网页上只做简单核对”。这决定构筑页以导入 → 快速核对 → 下载为主线；不代表阅读侧栏也以下载为中心，或弹窗需要承载完整阅读。其他界面的任务先依据现有产品契约提出建议，再通过具体流程验证，不把代理推断写成用户确认。

2026-10-24 时，构筑三稿与跨界面对照形成首轮探索，均未定案；11 月 15 日构筑已选择 A。接下来结合完整流程和体验反馈，决定哪些规则值得推广；不能先把网站稿定型，最后给扩展套皮。历史工坊列入界面盘点及差异说明，沿用功能冻结决定，不恢复模拟器研发；若公共导航调整影响其外壳，应单列影响和处理建议。

## 现状：事实与判断分开

2026-10-23 的检查基于 main `68da53e` 对应的本地页面和自造示例。线上入口触发 Cloudflare 验证，以下不是线上浏览器验收记录。

| 已观察事实 | 对设计的判断／待验证假设 |
| --- | --- |
| 导入空态最大宽 820px，标题、拖入区、示例、说明集中在多层框内 | 局促不等于整页空间不足；层层分隔和同屏信息竞争可能比单纯宽度更关键 |
| 构筑桌面布局固定保留 248px 文件列和 320px 导出列；1440px 下阶段表可用约 807px，1280px 下约 631px，而三阶段示例表宽 712px | 阅读被辅助功能挤压；应比较收起辅助操作后，寻找文件／下载是否仍容易 |
| 首页、扩展介绍已有共同字体、配色、导航；构筑入口和工作区的结构、密度变化明显 | 需要统一对齐、层级、内容与操作的衔接，不能仅凭相同颜色判定整体统一 |
| v4 原型从已导入状态开始，添加文件只显示模拟提示 | 首次导入缺少完整设计，必须作为独立状态补齐 |
| 检查时 OpenDesign 项目只有导入空会话，无消息和运行记录 | 原型有外部迭代，但当时工具主要用于存放与预览；后续应留下实际技能运行和比较结果 |

这些数字只描述旧基线，不是下一版的尺寸要求。以上假设须由候选的真实渲染和使用反馈验证。上述基线检查主要是网站；随后生成的跨界面样张已做本地浏览器检查，仍不能替代真实扩展的整体体验复查。不能仅凭用户的网站例子推断扩展所有界面都有同样的空间问题。

## 全产品界面地图

以下是设计范围与任务假设，不是逐项重写清单。先记录现状、优先问题和证据，再决定保留、调整或深入探索。每项都需覆盖正常、空白、处理中和失败等实际存在的状态。

| 界面 | 主要任务与建议重心 | 需要结合功能保留的差异 |
| --- | --- | --- |
| 网站首页、扩展介绍与安装指引 | 理解两件工具、判断适用性、进入工具或安装扩展 | 可以舒展；示意沿用真实产品语言，下载与适用条件靠近，不能演变成不同品牌的独立章节 |
| 构筑导入、结果、核对与下载 | 用户已确认先得到中文文件，必要时简单核对 | 主流程短；长内容与阶段比较按需查看，多文件关系和输出范围仍清楚 |
| 扩展工具栏弹窗 | 判断当前页能做什么、是否生效，然后发起操作 | 按当前页收放；短任务优先，不塞入网站导航或完整攻略正文；离开后再打开的状态要可理解 |
| 攻略范围选择与阅读侧栏 | 选对内容、明确主动翻译、连续阅读与必要对照 | 正文获得空间，范围、进度和返回位置有依据；控制区不能压缩正文，待核对不能伪装成译文正确 |
| 翻译设置、连接反馈与站点管理 | 配置服务，理解限额和权限，安全返回原任务 | 表单分组和保存状态一致；草稿、失败恢复、删除后果保持原契约，不为了整齐隐藏决策信息 |
| CoE 中文搜索候选、装备转换和状态提示 | 在原站任务中找到对象、核对转换结果并交给原站确认 | 紧凑、低干扰；候选与装备文字优先，保留非官方身份、原站上下文和最终确认 |
| 网页范围选取提示、原文旁译文与划词气泡 | 在当前阅读位置选取、理解、返回原文 | 适应宿主页浅深色、字号与视口；统一操作语义和反馈，不强铺网站黑底或大标题 |
| 通用反馈、空态、错误、确认与帮助 | 知道发生了什么、能继续做什么 | 同类状态使用同类表达，但提示位置、持续时间和占用空间随任务变化 |
| 历史工坊及边缘入口 | 说明可用范围，避免入口产生错误预期 | 记录与当前设计的差异；冻结功能不因本轮整体设计自动恢复开发 |

扩展能力和真实验证范围以[扩展开发索引](chrome-extension/development.md)及[兼容性记录](chrome-extension/compatibility.md)为准。后续盘点至少记录：界面／状态、任务、截图来源、问题假设、共享规则、合理差异、下一步验证。不得把“未检查”写成“已统一”。

## 方法来源与本项目的采用方式

[Railcode 的设计过程](https://railcode.dev/blog/vibe-coded-website)提供了四点启发：先探索差异明显的候选；保留分稿并排比较；用可实时调节的面板缩短试错；整体满意后再进入生产实现。文章也展示了独立视觉元素如何通过重新构图融入整页。我们借用探索与比较的方法，不复制其资产、页面或营销动效，不将作者的模型偏好视为普遍结论。

本项目据此采用以下工作原则：

1. **先确定当前任务，再分配空间。** 阅读、比较、核对、导出各有主次；把低频功能收起时，同时验证它是否仍能被找到。
2. **每轮只验证少数假设。** 结构轮主要改变信息组织，保持数据与视觉基础一致；不要同时换颜色、字体、文案和布局，导致无法解释变化原因。
3. **备选必须改变体验。** 只更换按钮颜色、边框或左右镜像，不算新的结构方向。保留有价值的反例，记录为什么放弃。
4. **先看整条流程，再精修单个控件。** 同时检查构筑交付、弹窗进入阅读、设置后返回、CoE 搜索与装备转换等流程；再把关键界面放在一张对照板上看整体关系。
5. **用真实密度验证。** 自造样本也要包含长名、多阶段和未收录内容。小样本漂亮不能替代实际信息密度下的阅读。
6. **说明与操作相邻。** 本地解析说明靠近导入；游戏加载待验收靠近下载；待核对原因靠近对应内容。删重复解释，保留决策所需事实。
7. **先让用户体验，再讨论尺寸。** 用户描述“挤、空、跳、找不到”即可；代理负责将感受转成可验证的问题和候选。

## 推荐方向与仍需比较的可能性

保持冷蓝黑、直角、钢蓝主操作、中文衬线与游戏语义色。优先重新分配空间、减少容器嵌套、建立页面连续性。相关规则如确需改变，应单列原因与影响，不能由通用技能静默改写。

### 总推荐：共同规则、任务差异、局部验证

**先建立全产品的共同表达，再由代表性界面验证它是否合用，最后按完整使用流程分批迁移。** 每一条共享规则都要回答“用户因此更容易理解什么”；同一布局在两处都能使用，才考虑复用，不能把视觉一致误写成所有界面同宽、同密度、同样多的框。

| 层次 | 共同部分 | 允许因任务变化的部分 |
| --- | --- | --- |
| 视觉与身份 | 字体角色、色彩含义、控件形状、品牌署名、标题与正文关系 | 标题大小、留白比例、装饰强度；宿主页内结果适应原站背景和正文 |
| 操作与反馈 | 主次操作区分、选中与禁用、焦点、加载／成功／失败、关闭与返回的含义 | 控件的位置、是否吸顶、内联展开或分步；按窗口和任务决定 |
| 信息组织 | 先当前任务，再必要依据，低频细节可找到；同一概念名称一致 | 弹窗快速启动、侧栏持续阅读、设置逐项配置、构筑快速交付各有主次 |
| 内容表达 | 真实术语、未收录与失败的区别、非官方边界、清楚的动作文案 | 确定性词典结果与模型译文分别说明可信范围；不共用模糊的“已完成”掩盖差异 |

先做“共享规则样张”：用少量真实示例展示标题、正文、主次按钮、选择项、处理中、失败和待核对。再用网站、弹窗、侧栏、设置、CoE 浮层及浅／深宿主页中的气泡共同检验。样张是探索工具，不能形成另一份正式 token 或组件库。

比较优先围绕**框的层级、内容与操作比例、信息展开方式**。可试较少分隔的内容流，也可试有明确分区的工具布局；每种方法都要在窄弹窗和长文侧栏上检验。不要同时另选品牌色、字体和动效，以免无法判断结构变化的作用。

### 各类界面值得验证的可能性

以下是代理的起始建议，尚未由用户选定。每轮选择最影响体验的问题验证，不要求每个界面都制作多份完整稿，也不为比较而新增产品能力。

| 界面／问题 | 优先建议 | 另一种可能及其代价 | 让用户实际体验什么 |
| --- | --- | --- | --- |
| 网站入口如何衔接工具 | 用共同的内容示例和操作名称串起两件工具，进入工具后自然收紧空间 | 两工具分别讲完整故事，适合独立传播，但入口和示意更易重复、割裂 | 从介绍进入工具，是否仍认得刚才看到的内容和下一步 |
| 弹窗是否信息过多 | 当前页状态和当前可做的动作优先，其他能力保留明确的次入口 | 全部能力常显，更容易发现功能，但会拉长弹窗、稀释当前任务 | 在 CoE 和普通攻略页分别打开，第一眼能否找到要做的事 |
| 阅读控制是否挤压正文 | 范围确认与阅读分成清楚的状态，进入阅读后控制区收简，随时可返回调整 | 范围、目录和正文同时可见，少一次切换，但窄侧栏里正文容易被压缩 | 读几段长文，查看原文或调范围，再回到刚才的位置 |
| 设置是否难找、难理解 | 按服务、限额、站点权限等目的分组，呈现当前问题相关说明 | 全部设置平铺，熟练用户查找快，但新用户不易分辨哪些必填；折叠过度也会隐藏必要信息 | 从未配置或连接失败出发，能否知道缺什么、改完如何返回；不能丢失草稿 |
| CoE 候选如何既清楚又紧凑 | 保留辨识对象所需的名称、类别、匹配字；详细内容按需查看 | 更多中英说明常显，降低打开详情的次数，但减少一屏候选数 | 在相似名称、长名称和无结果之间切换，能否准确判断应选哪项 |
| 划词结果是否打断阅读 | 常用操作和短结果直接呈现，长结果清楚展开／滚动，保留原文上下文 | 更多对照内容默认展开，信息更充分，但可能遮住正在读的段落 | 在浅／深页面和视口边缘查看一段长结果，再关闭或返回原文 |
| 反馈是否各说各话 | 同类状态共用词义和视觉信号，错误靠近可处理的位置 | 集中提示栏便于总览，但可能脱离具体失败项；短暂提示不适合需要修正的问题 | 发生部分失败时，能否知道哪一项受影响、其他内容能否继续使用 |

这些变化主要改变呈现与衔接，不自动改变权限、翻译请求、数据范围或产品能力。跨界面对照用于先找共同规则中的问题；涉及真实行为的取舍，随后进入对应完整流程验证。

### 构筑局部试验的三种假设

| 候选 | 用户首先看到什么 | 可能收益 | 必须验证的代价 |
| --- | --- | --- | --- |
| A：单页快速交付 | 已导入构筑／文件、处理结果、待核对提示和明确下载入口；详情按需展开 | 从导入到下载路径短，信息集中在当前任务 | 是否过度简化导致用户不放心；未收录项是否容易找到 |
| B：轻量核对工作区 | 精简结果列表和当前文件的核对区，下载始终容易找到 | 需要逐份查看时不必来回切换页面，适合多文件 | 核对区是否又挤压结果；无需查看时是否产生额外负担 |
| C：紧凑分步交付 | 先导入，再集中展示处理结果和导出选择；可返回调整 | 每一屏任务清楚，容易理解设置与结果关系 | 是否多出不必要点击；返回后状态能否保持；是否像强制向导 |

**当前推荐为 A：单页快速交付，属于代理建议，尚未选定。** 它直接响应用户的下载优先任务。B 检验轻量核对能否提升确定感，C 检验分屏聚焦是否值得增加操作。第一轮允许三者都不合适，也允许保留某个局部后另提组合；组合后仍须重新核对整体，不能直接拼接。

此前建议的宽幅阶段对照、当前阶段阅读与可收起目录，保留为“深入查看”中的组织可能性。用户优先级明确后，已撤回把阶段表作为默认首页的优先建议；并非删除现有阶段比较、逐项核对或多构筑管理能力。

首页与首次导入分别验证：

- 首页：围绕“读懂英文 PoE2 资料”串起两件工具；演示使用与工具一致的内容和表达，避免每个区块发展成独立的小界面。宣传面可更舒展，工具面可更紧凑，二者共享明确的导航、标题层级和对齐关系。
- 首次导入：比较“集中导入、结果示例辅助”与“操作和结果示例并列”。导入、粘贴、试用示例均要可发现，不能把示例入口变成强制教程。
- 下载：主要下载入口可找到，具体范围清楚；选项和实际导出内容按需要展开。只有一套构筑时避免两个视觉同级、结果近似的下载入口造成困惑，同时保留真实的单份／当前构筑／全部下载能力。

上述内容表达意图；顶栏、抽屉、内联展开等只是可选手段，原型可以提出更合适的实现方式。

## 推进路线与每轮交付

| 阶段 | 要解决的问题 | 交付 | 进入下一步的依据 |
| --- | --- | --- | --- |
| 0：全产品盘点 | 每种界面在帮用户做什么，哪里割裂 | 本文、界面与状态清单、基线截图、样本及旧稿快照 | 网站与扩展均有位置，事实、假设、未检查项明确 |
| 1：共同规则与代表试验 | 一套语言能否适应不同任务 | 共享规则样张、跨界面对照板、少量结构候选；进行中的构筑三稿纳入本阶段 | 至少能解释网站、弹窗、侧栏、设置与宿主页内界面的共性和差异；尚不冻结全局规则 |
| 2：完整流程 | 候选是否支持真实使用和界面切换 | 每条重点流程最多两套可点击候选；不做“所有界面乘三”的整站复制 | 用户可走通任务，关键取舍有具体体验依据 |
| 3：收敛与精修 | 各界面是否都清楚、舒适且可辨认 | 一套主候选；按需使用参数面板；跨界面状态与窗口检查记录 | 局部改进没有破坏共同规则；未处理反馈与例外明确 |
| 4：按流程迁移与复查 | 如何保持真实行为，避免新旧界面再度分裂 | 共享规则映射、对应界面实现、必要回归、原型与产品对照 | 每批覆盖完整任务并复查受影响界面；体验与工程证据分别成立 |

优先验证四条流程：构筑导入到下载；弹窗发起攻略范围选择到阅读、设置后返回；CoE 中文搜索到选择、装备转换到原站确认；划词触发到查看、关闭或返回原文。共享设计先从这些代表界面得到反馈，具体生产批次再根据问题严重性、实际使用频率和共享代码影响决定。当前主线仍为扩展，不能因第一份草稿是构筑页就把扩展排到最后。

不要为追求候选数量持续造稿。三份是第一轮探索上限，不是每轮必做指标；若某方向明显不适用，先解释原因并换一个有意义的候选。未选中稿只归档，不继续作为活动主稿维护。

每轮结束记录：本轮问题、变化、观察、用户原话、代理解释、保留／放弃／待验证项，以及下一轮的一个主要问题。截图、文稿和运行记录对应到具体候选，避免用旧截图证明新稿。

## 非专业用户如何参与

代理每轮先提供推荐及其理由，再邀请用户体验；不把设计判断整体交回用户。沟通采用“看到了什么 → 有哪些可能 → 我建议什么 → 请体验一个具体任务”。

| 用户表达 | 代理应继续查什么 | 可以拿来比较的建议 |
| --- | --- | --- |
| “还是挤” | 主内容宽度、同时可见信息、框的层数、阅读行距 | 收起辅助操作与减少容器层级分别试一次，说明各自影响 |
| “太空了” | 空白有没有支持主任务，内容是否被压到下方 | 调整内容比例或增加有用的结果预览，避免用装饰填空 |
| “像几套不同工具” | 网站与扩展的标题、控件、状态、术语、导航是否有共同规则 | 并排看代表界面，再实际切换任务；指出应共享的部分和功能造成的合理差异 |
| “找不到下载／当前阶段” | 控件是否被过度收起，状态是否只靠位置或颜色表达 | 保留清晰入口与当前上下文，同时收起低频设置 |

一次主要询问一个会改变方向的问题，例如“这两稿中，哪一个让你更容易确认文件可以下载？”允许回答“两者都不舒服”或只指出局部。不要要求用户选择 Grid、断点、组件库或精确像素。

可以自主处理可逆的细节和明显缺陷，并说明依据；涉及主要阅读方式、默认比较方式、现有能力取舍或品牌改变时，展示可体验结果后再由用户判断。无回复不等于选中候选；继续准备不依赖选择的样本、记录和检查。

## 样本、比较与验证

构筑局部试验用同一套自造内容比较三稿：空态、一套三文件／三阶段构筑的处理结果、展开一个词缀详情、一个待核对内容、导出范围与选项。默认不展开完整阶段表，保留深入查看入口。草稿标明模拟，不伪装成真正解析／翻译／下载成功。

扩展样本按任务准备：CoE／普通网页／不可操作页面下的弹窗；有层级的攻略与长正文、部分失败、范围预览；未配服务、配置草稿和连接失败；长站点名、权限拒绝与删除；中文搜索的无结果／多结果及长名称；装备转换的保留原文行；浅／深宿主页、靠近视口边缘的划词结果。均用合成内容与响应验证 UI，不发送真实 Key 或调用付费翻译，不重开已停止的语义质量周期。

进入完整流程后再扩大样本：

- 单文件构筑与单文件内等级范围；三阶段与更多阶段；多套构筑；长名称、长备注；无装备或缺少说明的合法文件。
- 文件错误、词典加载／失败、部分未收录、下载失败与恢复；简体和繁体各自用正式词典核对，不能互转造样本。
- 1280、1440、1920 桌面宽度和一档窄屏；用户实际窗口、浏览器字体或缩放有差异时补测。记录 CSS 视口和缩放，不仅写显示器分辨率。

同一界面的候选保持相同数据、视口、滚动位置和展开状态。跨界面对照尊重真实容器：弹窗用弹窗尺寸，侧栏用可调整窄窗口，网站用页面宽度，浮层放回宿主上下文。小尺寸并排缩略图用于判断共同关系；真实阅读与点击必须进入正常尺寸，不能把各界面缩放到一样大后宣称一致。

布局调节面板只供设计：允许调整内容宽度、辅助栏显示、行距和区块间距；保留一键回到基线及所选参数记录。它不自动成为产品设置，也不绕过生产令牌和字体门禁。

### 全产品体验判据

- 从不同入口进入后，能辨认这是同一组工具；相同动作、状态和术语有相同含义。
- 当前界面的主要任务最显眼；快速操作不被大段说明打断，长文阅读不被操作框长期挤压。
- 进入设置、详情或权限操作后，能回到原任务，合理保留范围、输入、草稿和阅读位置。
- 正常、处理中、失败、部分可用和待核对有明确区别；用户知道下一步，且不会被虚假成功提示误导。
- 扩展自有界面有共同身份；原文旁译文与划词仍适应宿主。符合宿主页的外观差异应有依据，不算天然失败。
- 每个代表界面都验证键盘、焦点、长内容、窄窗口与必要反馈；网页模拟不替代真实 Chrome 弹窗、侧栏、权限和宿主页验收。

### 构筑局部体验判据

- 首次进入能找到导入／示例入口，并理解文件本地处理。
- 处理完成后能快速判断哪些文件可下载、哪些处理失败、哪些内容保留原文；“未收录”不等于文件损坏，也不虚构必须逐项确认后才能下载的新门槛。
- 能判断当前构筑、阶段、语言及导出范围；文件数量不会遮蔽构筑关系。
- 常见三阶段基准样本在普通桌面宽度有足够对照空间；若仍需横滚，说明原因并比较其他组织方式。更多阶段采用明确浏览策略，不以缩小文字强行塞满。
- 展开详情后仍能辨认对应阶段和装备；长名与长备注可读完整内容。
- 从首页进入工具、从处理结果进入核对或下载时，导航与操作预期连续；无需深入阅读也能完成默认任务。
- 找得到下载，理解选项影响；显示方式和文件实际输出不混淆。
- 键盘、焦点、对比度、减少动效及窄屏能力遵循已有基线；原型检查与生产验收分开记录。

体验结论记录为“支持此方向／发现代价／仍需用户体验”，不使用一个审美总分替代问题。工程通过、截图无溢出、模型自评，都不能单独证明用户满意。

## OpenDesign 的实际工作方式

沿用“PoE2 Tools 改版 v4”和同一个原地项目目录。活动设计仍在既有目录，轮次草稿和快照放在项目内子目录；这属于版本比较，不是另建一套主设计。

1. 先核对项目、设计系统、技能内容和执行器；已绑定品牌规则优先于技能的一般审美建议。
2. 用实际生成任务委托技能，记录技能、简报、运行状态和产物。只有安装／读取／预览时，如实记录，不写成技能已完成设计。
3. 设计简报始终携带全产品范围和共享依据，再指定当前任务界面；不能每开一页就重新发明风格。大范围改稿前保存本地快照并核对；OpenDesign 与代理不同时编辑同一目标。一次生成期间，代理可整理正式文档，但不抢写生成目标。
4. 技能完成后读取产物，核对预览对应本轮入口及文件版本，实际打开并检查交互，再提出反馈。任务链完成与局部运行完成分别确认；链接存在或单段运行成功都不能单独证明交付完成。若生成失败，保存原因并使用已验证的官方路径恢复；不静默换成手写稿并冒称工具产物。
5. 每轮把推荐、代价和待选问题带回用户；获确认的规则才同步 DESIGN、文案及设计系统副本。

2026-10-23 核对的技能分工：

| 技能 | 本轮用途 | 使用限制 |
| --- | --- | --- |
| `frontend-design` | 依据既有品牌生成跨界面对照、结构候选和可点击流程 | 本机有实际工作流内容；当前先生成探索稿，不直接改生产代码 |
| `impeccable-design-polish` | 已有候选的层级、间距、响应式与交互精修 | 本机有实际内容；不等同于用户级完整 impeccable，不重复跑两套完整流程 |
