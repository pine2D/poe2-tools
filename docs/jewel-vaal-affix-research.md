# 珠宝瓦尔增删词缀核对

核对日期：2026-09-18。当前代码提交：`641ba04`。这是机制证据与接入边界记录；v116 已有本地实现，发布与生产验收尚待完成。

## 已取得的证据

[sirgog 原创视频](https://www.youtube.com/watch?v=YVDDZ6xVpCI)发布于 2025-01-24，珠宝章节为 20:39–21:56。21:30–21:41 的作者讲解明确表示：瓦尔的一种结果会随机增加或移除一个词缀，新增可以突破普通珠宝四条、两前两后的常规限制。已核对相应画面：这是讲解幻灯片，不是珠宝施加通货前后的游戏操作录像。

视频和已登记的 [同作者文字攻略](https://mobalytics.gg/poe-2/guides/vaal-corrupting)属于同源材料，不能算独立交叉实测。没有采用视频中的概率。作者关于传奇的其他结论不用于本项目，用户要求的传奇和咒符仍只读。

本轮搜索出现的 0.5 五词缀珠宝攻略主要讲液态轻蔑增容、亵渎填充和移除增容工艺；它们描述的终点不是瓦尔新增第五条，不能用于证明这项腐化操作。本轮尚未取得 0.5 珠宝瓦尔增删的明确前后实操画面。

## 接入前的实现与影响

- `corruptionRules.ts` 只声明不变、加孔、强化和顺序重选，没有单独增加／移除显式组的操作。
- `craftSteps.ts` 对瓦尔重选复用有序替换，新增或移除必须是独立结果，不能伪装成普通崇高／剥离，否则可能错误计费、放开后续制作或复用错误容量。
- `affixCapacity.ts` 将稀有珠宝超过单侧两条的状态纳入 `usesJewelCapacity`；`rehearsal.ts` 和 `craftProject.ts` 因此要求液态情感来源。这个门禁服务于现有液态增容模型，不能直接当作腐化新增的来源证明。
- 现有稀有珠宝已有状态最多每侧三组、合计五组；普通新增容量仍是两前两后，明确的液态工艺才增加对应空位。接入腐化不得全局提高普通制作容量。
- 导入一个已腐化五词缀珠宝，不能仅凭最终文本推断第五条来自瓦尔还是此前液态增容。项目内实际操作链与外部导入的历史未知应分别处理。

## 下一项完整交付的边界

可依据原创说明建立明确标注的指定结果模型，先贯通普通稀有珠宝单次新增／移除；这是现有腐化模型的扩展，不是游戏随机成功率。必须同时覆盖候选资格、冲突组、数值、实例身份、腐化锁定、三语导出、完整未来历史、撤销恢复及单颗瓦尔费用。每项限制应说明是本工具未核实，不能宣称游戏禁止。

下列事项仍需独立证据：普通／魔法珠宝变更稀有度、已有五词缀继续腐化的最高侧别与总量、范围珠宝、破裂保护、工艺／亵渎及特殊容量交互。不从“一种结果能突破上限”推断所有组合。局部模型交付不能作为完整模拟目标完成的证据。
